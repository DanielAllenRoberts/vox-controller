## 1. Scheduler — reminders / timers / alarms (idea #16)

**Goal (your words):** "remind me in 15 minutes", "set a 20-minute timer", "remind me
at 10:55 PM", repeating ("remind me every day at this time"), and **cancel** them — all
visible on their own **dashboard page** showing every cron currently running.

**Key decision (proposed): Vox owns the scheduler core — with an optional Apple mirror.**
One unified "scheduled job" model covers timers, alarms, and reminders (they differ only in
how the time is expressed, whether they recur, and how they announce). Vox owning them is
the only design where the dashboard can *show and cancel everything in one place* — the
feature you asked for. **On top of that, optionally mirror a job to Apple so it can also
fire on your phone** (see "Native integration" below).

**Output policy per kind (your refinement):**
- **Reminder → spoken** (the point is the message): personalised via your name from core
  memory — *"Hey Daniel, reminding you to go fetch the kids."* (+ a soft sound).
- **Timer → sound only** by default (*"timer's up"* chime); the label is usually obvious.
- **Alarm → both** — a sound *and* a spoken line.
- All configurable; the per-kind default above is just the starting point.

**Native integration — "also goes off on my phone" (researched 2026-06-19):**
- macOS **Clock.app alarms/timers do NOT sync to iPhone** (device-local) *and* Clock isn't
  AppleScript-scriptable — so Clock is a dead end for the phone goal.
- The native path that **does** reach your phone is **Apple Reminders** (AppleScript-
  scriptable *and* iCloud-synced) — a timed reminder notifies on every signed-in device.
  Calendar is the same idea for events.
- **`shortcuts` CLI is present** — macOS Shortcuts *can* drive the local Clock, but its
  Clock actions are limited/version-dependent and still device-local. A quick spike, lower
  priority than the Reminders mirror.
- **Plan:** build the Vox scheduler core first; then add an **optional "also add to Apple
  Reminders" mirror** (config/voice toggle) for cross-device. Clock-via-Shortcuts is a
  stretch spike only if we want a real on-Mac Clock timer too.

**Storage (proposed):** `data/reminders.json` (gitignored), matching the existing
`data/*.json` store pattern. Not SQLite — that's a separate cross-cutting migration (#27).
Job shape: `{id, kind: timer|alarm|reminder, text, fire_at (ISO), recurrence: null|daily|weekly|…, created_at, enabled}`.

**Engine:** a background **scheduler thread** started with the daemon (the voice loop is
synchronous, so this must be its own thread). It wakes every ~5–10 s, fires any due job
per the output policy above (sound and/or spoken line), then either deletes a one-shot or
rolls a recurring job to its next occurrence.
Persisted to disk so it survives a `restart`; on startup, fire recently-overdue one-shots
once ("while you were away…") and drop stale ones; recurring jobs just resume.

**Parsing:** deterministic-first for the obvious shapes ("set a timer for N minutes",
"remind me at H:MM") to stay fast and free; natural phrasing ("every weekday at quarter
past seven") falls through to the small brain, which returns a structured schedule — same
translate-to-action pattern as the executor (#12). Cancellation by voice ("cancel my
timer", "cancel the 3 pm reminder") and a delete button on the dashboard page.

**Plan:**
- 1a. `scheduler.py` — store + background thread + fire (sound + TTS). → **verify:** "set a timer for 10 seconds" speaks/sounds ~10 s later; persists across `restart`.
- 1b. Voice parse for create + cancel (deterministic, then brain fallback). → **verify:** the four phrasings (relative, absolute, recurring, cancel) each create/cancel the right job.
- 1c. Dashboard **Scheduler** page + `/api/reminders` CRUD + WS for live countdown. → **verify:** page lists active jobs, counts down, cancel works, and reflects voice-created ones live.

## 2. Active-app visibility + AX-tree vision (ideas #18, #36)

**Goal (your words):** the system should "see which app I'm on right now"; make sure the
**AX tree** works well (test it by **turning off the screenshot system**); and unlock
**per-app command sets** — "search" on YouTube ≠ "search" on the web; Cursor unlocks
Cursor-specific verbs — stored separately and **filtered by the active app**.

**The gap:** `environment_context()` lists *running* apps but never the **focused** app or
the **active tab**. `web/axtree.py` reads the AX tree but only the dashboard consumes it —
it's not a brain vision source.

**Slice 2a — focused app + active tab into context (small, high-leverage).** Add
`frontmost_app()` and active-tab (title + URL) helpers in `actions.py`; fold both into
`environment_context()`. This one change tells the brain which app you're on *and* feeds
slice 3 (tab matching). While here, also fold in **time awareness** (idea #47) — `Now: Thu
2026-06-19 14:32 (Europe/London)` — same context block, and a **prerequisite** for the
scheduler's "in 20 min / tomorrow at 9" parsing. → **verify:** focus an app, trigger an
escalation, and the prompt's environment block names the focused app, active tab URL, and
current date/time/zone.

**Slice 2b — AX tree as the default "see my screen" (proposed flag).** Wire
`axtree.snapshot()` → compact text into the brain's vision path behind a new
`screen_vision_mode` config: `axtree` | `screenshot` | `auto`. Testing the tree =
`axtree` + screenshot disabled. → **verify:** with `axtree`, "what's on my screen" answers
from the tree (no screenshot), and the tree text is token-cheap vs the image.

**Token logging for the AX-tree path (your refinement).** Record the AX-tree vision call
in the existing usage ledger (`usage.record_usage`) under a distinct `kind`
(`vision_axtree` vs `vision_screenshot`) so the Token Usage page already breaks out its
input/output tokens — letting us measure cost *and* effectiveness (tree-vs-screenshot) over
real use. → **verify:** an AX-tree "what's on my screen" call shows up on the Token Usage
page tagged `vision_axtree` with its token counts.

**Slice 2c — per-app command profiles (the deep one; likely a later session).** The same
phrase resolves differently by focused app/site, scoped through the existing rules store
(`web/rules.py`, Rules page) with an optional `app`/`site` field; the router picks the
active profile from `frontmost_app()`/active tab. Flagged here so we design 2a with it in
mind, but it's the biggest piece and I'd do it after the quick wins land.

## 3. Tab visibility on Arc (idea #36, near-term)

**Goal (your words):** Arc tabs aren't matched well — a new/generic-titled tab isn't
recognised, so it escalates to the LLM, but the LLM can't see all the tabs either, so it
can't make an educated guess.

**Fix (already identified in #36):** surface each tab's **URL/domain** (not just title)
*and* the **active tab** in `environment_context()`, so both the fuzzy matcher and the
brain can tie "go to Google Docs" to a `docs.google.com` tab even when its title is
"Untitled". Small change to `environment_context()` + `_tab_titles`/`_tab_urls` (the URL
helper already exists). **This rides on slice 2a** — same context enrichment.
→ **verify:** open a generic-titled doc; "go to my Google Docs tab" resolves to it instead
of guessing/failing.

## 4. Conversation viewer (idea #43)

**Goal (your words):** chats live in RAM/temp storage — a dashboard tab to **see what it
remembers during a session**, including when **multiple sessions** are running.

**Design (proposed): mirror `usage.py` exactly.** Conversation history is `history = []`
local to the mode loops — pure RAM. Add a `conversation` pub/sub module (in-RAM ring
buffer + `subscribe`/`publish` like `usage.py`), publish each turn (your utterance, the
brain reply, which brain, any command that ran) from the loop, expose
`/api/conversation/recent` + `/api/conversation/stream` (WS), and add a **Conversation**
dashboard page that renders it **like a standard AI chat** (user/assistant bubbles,
which brain replied, any command that ran inline). **Ephemeral by design — nothing written
to disk;** the persistent layer stays the tiered memory (#28/#29).
→ **verify:** start a chat, watch turns appear live on the page; refresh shows the in-RAM
buffer; nothing new appears under `data/`.

## Sequencing

**3 → 2a → 4 → 1 → 2b**, because:
- **2a + 3 are the same change** (enrich `environment_context` with focused app + active
  tab + URLs) and the highest value-per-line — do them together first.
- **4 (conversation viewer)** is self-contained and mirrors an existing pattern — a clean,
  satisfying quick win.
- **1 (scheduler)** is the biggest net-new feature (thread + store + parse + page); do it
  once the quick wins are in.
- **2b (AX-tree vision)** is an isolated flag + wiring; slot it when convenient.
- **2c (per-app command profiles)** is the deepest design — likely its own session.

Each slice ships behind its own verify check; nothing merges until it passes. Dashboard
slices need a `dashboard/dist` rebuild (the bridge serves dist, not the dev server).
Nothing is committed without explicit OK (public repo).
